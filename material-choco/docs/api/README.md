# Hub HTTP API

All bodies are JSON objects. Browser routes need the session cookie from `POST /api/login` (or from a passkey sign-in) and refuse cross-site requests. Agent routes need `Authorization: Bearer <agent token>`. Errors are `{ "error": "message" }` with a 4xx or 5xx status.

## Roles

Every account has one role. The account created by `POST /api/setup` is an `admin`. The desktop app has one local user, who is always `admin`.

| Role | May do |
| --- | --- |
| `admin` | Everything, including users, webhooks, removing machines, and machine policy (read only, allowed commands). |
| `operator` | Run any command, cancel jobs, pair machines, rename and group machines, create and edit schedules. No user management, no webhooks, no machine removal, no change to machine policy. |
| `viewer` | Read everything the other roles can read (machines, jobs and their output, schedules, history). May queue an inventory refresh and plain read only queries: `list`, `outdated`, `search`, `info`, and the `list` subcommand of `pin`, `source`, `config`, `feature` (plus `config get`), with display and filter options only. |

A request that the role does not allow gets `403`. Role changes, disabling and deleting an account take effect on the next request of that account's open sessions.

Job output and the history are visible to every role. Do not give an account to someone who should not read them.

## Sign in and status

`GET /api/status` (no session needed) answers:

```json
{ "product": "Material Choco", "version": "0.1.0", "builtAt": null, "commit": null, "desktop": false,
  "setupNeeded": false, "authenticated": true, "user": "admin", "role": "admin",
  "passkeysAvailable": true, "roles": ["viewer", "operator", "admin"],
  "hubTime": "2026-11-16T10:00:00.000Z", "timezone": "UTC", "tls": false, "hostname": "hub" }
```

`role` is `null` when not signed in. `passkeysAvailable` is true when the address the request came in on can use passkeys: HTTPS or `localhost`, and a host name rather than an IP address.

| Route | Body | Answer |
| --- | --- | --- |
| `POST /api/setup` | `{ name, password }` (once, creates the first `admin`) | `{ ok: true }` and the session cookie |
| `POST /api/login` | `{ name, password }` | `{ ok: true }` and the session cookie. `403` for a disabled account (only after a correct password). `429` while locked out. A `totp` field is ignored. |
| `POST /api/logout` | none | `{ ok: true }` |
| `GET /api/account` | | `{ name, role, totpEnabled, passkeys, passkeysAvailable, desktop }` (`passkeys` is a count; `totpEnabled` is always `false`, see below) |
| `POST /api/account/password` | `{ current, next }` | `{ ok: true }`. The account's other sessions are signed out. |

### Authenticator codes were removed

The hub has no authenticator code (TOTP) step. Sign-in is a password or a passkey.

- `POST /api/account/totp` no longer exists and answers `404`.
- `POST /api/login` ignores a `totp` field and never answers `totpRequired`.
- `totpEnabled` is still present in `GET /api/account` and in each item of `GET /api/users`, and is always `false`. It is kept so that an interface written for the earlier version keeps working, and will be dropped later.
- A hub upgraded from a version that had authenticator codes deletes every stored authenticator record when it starts and writes one history entry per affected user: `account.totp.removed` with `target` (the user name) and `wasEnabled`. The secret is not written anywhere. Those users sign in with their password alone from then on, so add a passkey if you want more than a password.

## Passkeys

Passkeys (WebAuthn) are an extra way to sign in. The password stays as the fallback. The hub asks for no attestation and ignores the attestation statement, so it never trusts a claim about the authenticator model. ES256 (P-256) and RS256 keys are accepted.

Binary values are base64url text, the same shape as `PublicKeyCredential.toJSON()` and `PublicKeyCredential.parseCreationOptionsFromJSON()` / `parseRequestOptionsFromJSON()` in browsers.

The relying party id and the expected origin are taken from the request `Host` header (and `X-Forwarded-Proto: https`, or the hub's own TLS). When the hub sits behind a proxy that changes `Host`, set `MATERIAL_CHOCO_ORIGIN`, for example `MATERIAL_CHOCO_ORIGIN=https://hub.example.com`. A passkey only works on the host name it was registered on.

### Add a passkey to the signed-in account

1. `POST /api/account/passkeys/begin` with `{ "password": "<current password>" }`. Answer:

```json
{ "publicKey": { "challenge": "<base64url>", "rp": { "id": "hub.example.com", "name": "Material Choco" },
  "user": { "id": "<base64url>", "name": "admin", "displayName": "admin" },
  "pubKeyCredParams": [{ "type": "public-key", "alg": -7 }, { "type": "public-key", "alg": -257 }],
  "timeout": 300000, "attestation": "none", "excludeCredentials": [{ "type": "public-key", "id": "<base64url>" }],
  "authenticatorSelection": { "residentKey": "preferred", "userVerification": "preferred" } } }
```

2. Call `navigator.credentials.create({ publicKey })` and send the result: `POST /api/account/passkeys/finish` with `{ "id": "<credential id>", "response": { "clientDataJSON": "<base64url>", "attestationObject": "<base64url>", "transports": ["internal"] }, "name": "My laptop" }`. Answer: `{ "ok": true, "passkey": { "id", "name", "alg", "createdAt", "lastUsed", "transports", "backedUp" } }`.

`GET /api/account/passkeys` lists the account's passkeys in that shape. `DELETE /api/account/passkeys/:id` removes one. An account can hold 20.

### Sign in with a passkey

1. `POST /api/login/passkey/begin` with `{}` or `{ "name": "admin" }`. Answer: `{ "publicKey": { "challenge", "rpId", "timeout": 300000, "userVerification": "preferred", "allowCredentials": [] } }`. Without a name the list is empty and the browser offers the passkeys it holds for this site. With a name the list holds that account's credential ids, which security keys without storage need. An unknown name gets one made-up id, so the answer does not show whether the account exists.
2. Call `navigator.credentials.get({ publicKey })` and send the result: `POST /api/login/passkey/finish` with `{ "id": "<credential id>", "response": { "clientDataJSON", "authenticatorData", "signature", "userHandle" } }`. Answer: `{ "ok": true }` and the session cookie.

Rules the hub applies:

- A challenge works once and for five minutes.
- The origin, the relying party id hash and the user-present flag must match. The signature is checked over `authenticatorData` followed by the SHA-256 of `clientDataJSON`.
- The sign counter must move forward. A counter that does not is refused and written to the history as `account.passkey.counter`, because the passkey may have been copied. Authenticators that always report 0 are accepted.
- Both open routes are limited to 60 requests a minute per address, and five failed attempts in a row lock passkey sign-in for that address with growing delays. Failed attempts answer `401` with the same message whatever the reason, and the reason is in the history. A disabled account answers `403`, only after a valid signature.

## Users

Administrators only. Not available in the desktop app.

| Route | Body | Answer |
| --- | --- | --- |
| `GET /api/users` | | `[{ name, role, disabled, createdAt, lastLogin, totpEnabled, passkeys }]` |
| `POST /api/users` | `{ name, role, password }` (`role` defaults to `viewer`; password of 10 characters or more) | the user |
| `PATCH /api/users/:name` | any of `{ role, disabled, password }` | the user |
| `DELETE /api/users/:name` | | `{ ok: true }` |

Names are 2 to 40 letters, digits, dot, dash, underscore or `@`, and unique whatever the case. The last enabled administrator cannot be deleted, disabled or given another role (`409`). Disabling, deleting, or resetting another user's password ends that user's sessions. Every action is written to the history: `user.create`, `user.role`, `user.disable`, `user.enable`, `user.password`, `user.delete`.

## Machines and the command allow list

`GET /api/machines` items gain two fields:

- `allowedCommands`: `null` (no restriction) or a sorted list of choco command names the hub accepts for this machine. Set it with `PATCH /api/machines/:id` and `{ "allowedCommands": ["list", "outdated", "upgrade"] }`. `null` or `"all"` removes the restriction. An empty list allows inventory refreshes only. Aliases are stored under the command's own name (`find` becomes `search`). Administrators only.
- `agentAllowedCommands`: `null`, or the list the agent on that machine enforces by itself. It is set on the machine with `--allow` and the hub cannot change it:

```
MaterialChoco.exe --agent enroll --hub https://hub.example:8443 --code XXXX-XXXX --allow list,outdated,upgrade
MaterialChoco.exe --agent run --allow list,outdated        # change it later; "--allow all" removes it
```

A job for a command outside either list is not created: `POST /api/jobs` reports the machine under `skipped` with the reason, the same way as for read only machines. Schedules skip such machines. An agent refuses such a job itself even when the hub sends it. Inventory refreshes only run fixed read only queries and are always allowed.

`PATCH /api/machines/:id` with `readOnly` or `allowedCommands` needs the `admin` role. `name` and `groups` need `operator`.

## Jobs and schedules

A job `spec` is `{ "kind": "choco", "command", "subcommand", "args": [], "options": {}, "global": {} }` or `{ "kind": "inventory" }`. Option ids are the ones in `shared/choco-schema.json`.

`POST /api/jobs` takes `{ machineIds: [], spec }` and answers `{ jobs: [], skipped: [{ machine, reason }] }`.

`GET /api/schedules` and the answers of the schedule routes show `********` in place of option values that the schema marks secret. Sending `********` back in a `PATCH` keeps the stored value.

## Webhooks

Administrators only. A webhook is an HTTPS address that receives one JSON `POST` per event. Plain HTTP is accepted for `localhost`, `127.0.0.1` and `[::1]` only.

| Route | Body | Answer |
| --- | --- | --- |
| `GET /api/webhooks` | | `{ events: [], formats: [], webhooks: [] }` |
| `POST /api/webhooks` | `{ name, url, format?, events?, offlineMinutes?, enabled? }` | the webhook |
| `PATCH /api/webhooks/:id` | any of the same fields | the webhook |
| `DELETE /api/webhooks/:id` | | `{ ok: true }` |
| `POST /api/webhooks/:id/test` | none | `{ ok, status, attempts, error? }` after one attempt |

A webhook is `{ id, name, url, format, events, offlineMinutes, enabled, createdAt }`. Defaults: `format` `json`, `events` `["job.failed"]`, `offlineMinutes` 10 (2 to 10080), `enabled` true. A hub holds up to 20.

Events:

| Event | Sent when | Extra field in the `json` format |
| --- | --- | --- |
| `job.failed` | a choco job ends with a non-zero exit code, is rejected by the agent, or times out | `job: { id, machine, machineId, command, state, exitCode, by }` |
| `job.succeeded` | a choco job ends with exit code 0 | the same |
| `machine.offline` | a machine has not been seen for `offlineMinutes`. Sent once per outage. Time during which the hub itself was stopped does not count. | `machine: { id, name, lastSeen, offlineMinutes }` |
| `login.lockout` | failed sign-ins lock a name or address out | `login: { name, ip, seconds, method }` |
| `test` | the test route is called | `test: true` |

Formats:

- `json`: `{ "event", "at", "hub", "text", ... }` with the extra field above.
- `discord`: `{ "content": "<text>", "allowed_mentions": { "parse": [] } }`, so a machine or package name can never ping anyone.

`command` is the redacted command line: values of options marked secret appear as `********`. Job output is never sent.

Delivery: 8 second timeout, redirects are not followed, and a failed delivery is retried up to 3 times (after 1, 5 and 15 seconds) when the receiver cannot be reached or answers 408, 429 or 5xx. The result is written to the history as `webhook.delivered` or `webhook.failed` with the webhook name, the event, the receiver's host name, the status and the number of attempts. The address itself is never written to the history, because for most receivers it is a credential.

An administrator can point a webhook at any HTTPS address the hub can reach, including addresses inside your network.

## Secrets at rest

On first start the hub creates `secret.key` (32 random bytes as hex, mode 0600) in the data directory and encrypts with AES-256-GCM:

- values of options marked `secret` in `shared/choco-schema.json` (source and certificate passwords, API keys, the proxy password) inside queued jobs and inside schedules,
- webhook addresses.

A job's secret values are decrypted only when the job is handed to its agent, and removed from the stored job when it finishes, is cancelled or expires. Data written by an older version is encrypted during the first start of this version.

**What this protects:** a copy of `hub.json` on its own, such as a backup or a file attached to a support request.

**What this does not protect:** anyone who can read the whole data directory reads `secret.key` too and can decrypt everything. To keep the key apart from the data, set `MATERIAL_CHOCO_KEY_FILE` to a path on another volume or secret mount. Back the key up with `hub.json`: without it, queued secrets and webhook addresses cannot be read, and the hub refuses to start with a damaged key file rather than replace it.

Other limits to know about: positional arguments and options not marked secret are stored as they are; job output is stored as the CLI printed it; passwords are salted scrypt hashes and were never stored in plain text.

## Agent protocol

Unchanged, with two additive fields:

- `POST /agent/enroll` and `POST /agent/poll` accept `info.allow`, the agent's local allow list (a list of choco command names). The hub shows it as `agentAllowedCommands`.
- `POST /agent/poll` answers `{ jobs: [{ id, spec }] }` as before. Secret option values in `spec` are the real values.
